# Acceptance test plan data runbook

How to create, check and remove the data the acceptance test plan (ATP, sheet
`ATP_Mairie360`, tab « Info & Access ») expects on the instance it is played on: the four
supplied accounts and one short demonstration course. No deployment creates them: they
are created by hand, by an administrator, with the steps below. French version:
[`docs/fr/atp-data.md`](../fr/atp-data.md).

Everything else the ATP uses (service groups, projects, tasks, events, conversations, the
tester's own Manager account) is created by the ATP itself: do not prepare it.

**No password is written in this file, in a ticket or in a chat.** The four passwords are the
ones of the ATP sheet, kept in the team's password manager. Type them in the screens, or
read them into shell variables with `read -s` as shown below.

## What is created

| ATP account | E-mail | First name / last name | Role (`roles.name`) |
| --- | --- | --- | --- |
| Employee | `employe@mairie360.fr` | Camille Durand | `User` |
| Manager | `responsable@mairie360.fr` | Julien Moreau | `Responsable` |
| Mayor | `maire@mairie360.fr` | Isabelle Lefèvre | `Maire` |
| Administrator | `admin@mairie360.fr` | `Administrateur` (renamed) / `User` | `Admin`, the seeded account `id = 1` |

The first and last names are fictitious and must not appear in the sheet's passwords (the
password policy refuses a password containing the account's first or last name). The
Administrator exists already: it is seeded by Liquibase from the instance's `ADMIN_EMAIL`
with the first name `Admin`, which its sheet password contains, so it is renamed first.

Course « Prise en main de Mairie 360 »: origin `platform` (provided with the tool), level
`beginner`, not mandatory, three short modules, each with a public link and a short `other`
content, no quiz. The Employee, the Manager and the Mayor are enrolled: the learners'
catalogue only lists the courses an agent is enrolled in.

## Prerequisites

1. **The release the ATP tests is deployed on the instance**: the Core API that accepts a
   password containing the e-mail local part, the e-learning API and schema that know the
   course origin (`courses.source`), and the fronts.
2. **The administrator's credentials**: the `ADMIN_EMAIL` account of the instance and its
   current password, from the team's password manager (the first password is generated by
   `scripts/seal-secrets.sh` and stored there), and its second factor if it has one
   (authenticator application or a backup code).
3. **`ADMIN_EMAIL` is `admin@mairie360.fr`.** Check it by signing in to
   `https://login.<domain>/` with `admin@mairie360.fr` and the current administrator password.
   If another address is the administrator, two things, both by the person holding the
   instance's sealing rights:
   - change the address of account 1 to `admin@mairie360.fr` (Administration → Users → the
     administrator → « Adresse e-mail », or `PATCH /api/v1/admin/users/1/ {"email": …}`).
     Re-sealing alone changes nothing on a running instance: the Liquibase admin seed only
     writes account 1 while it still holds the template credentials;
   - re-seal `ADMIN_EMAIL` so the Secret matches the account (`ADMIN_EMAIL=admin@mairie360.fr`
     `./scripts/seal-secrets.sh <env> mairie360 <env>` on the group's Argo CD machine, see the
     header of `clusters/mairie360/instances/<env>/secrets.yaml`), commit the new
     `secrets.yaml` through a pull request and promote it like any change.

   Never decrypt the sealed value to check it.
4. **The four mailboxes `@mairie360.fr` are reachable by the team**: creating an account sends
   an invitation e-mail to it, and the ATP checks the password recovery e-mail (F5).

## Steps in the screens (preferred)

Sign in to `https://admin.<domain>/` as the administrator.

1. **Rename the administrator.** Users → the administrator's row → edit: first name
   `Administrateur` (or a real name of the team that the sheet password does not contain),
   Save. Then « Réinitialiser le mot de passe » of the same account: the sheet's
   Administrator password, twice. Sign out and back in with it.
2. **Create the three accounts.** For each line of the table above: Users → « Nouvel
   utilisateur », first name, last name, e-mail, a temporary password of your own (at least
   12 characters, it is replaced at the next step), Create. Open the new account, set its
   « Rôle » (`User`, `Responsable` or `Maire`), Save.
3. **Set the final passwords.** On each of the three accounts, « Réinitialiser le mot de
   passe » with the sheet's password of that account. An administrator reset clears the
   first-connection step: the testers sign in directly. The invitation e-mail sent at step 2
   stays valid for 7 days; ignore it.
4. **Create the course.** The e-learning screens create a course with the origin `internal`
   only: create it with the API call of the next section (step 5) so it carries the origin
   `platform`. If the API is out of reach, create it from `https://elearning.<domain>/` →
   « Nouvelle formation » with the content below; it then shows under the origin « internal »,
   which the ATP does not check.
5. **Enrol the learners.** `https://elearning.<domain>/` → the course → « Agents inscrits » →
   « Inscrire des agents »: Camille Durand, Julien Moreau, Isabelle Lefèvre.

## Same steps with the API (fallback, and the course)

The APIs are not exposed on the internet: reach them from the instance machine with a port
forward (the SSH access is described in the `ansible` repository).

```bash
ssh -L 3000:127.0.0.1:13000 -L 3006:127.0.0.1:13006 ubuntu@<instance-ip>
# on the machine, in that session:
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
sudo -E kubectl -n mairie360-<env> get svc | grep -E 'core-api|elearning-api'
sudo -E kubectl -n mairie360-<env> port-forward svc/<core-api-service> 13000:<its port> &
sudo -E kubectl -n mairie360-<env> port-forward svc/<elearning-api-service> 13006:<its port> &
```

On your own machine (`curl` and `jq`), with `CORE=http://localhost:3000` and
`ELEARNING=http://localhost:3006`:

```bash
read -rs -p 'Administrator password: ' ADMIN_PW; echo
JWT=$(curl -sS -D - -o /dev/null -X POST "$CORE/api/v1/auth/login" -H 'Content-Type: application/json' \
  -d "$(jq -n --arg e admin@mairie360.fr --arg p "$ADMIN_PW" '{email:$e,password:$p,device_info:"atp-runbook"}')" \
  | sed -n 's/^[Aa]uthorization: Bearer \(.*\)\r$/\1/p')
```

An empty `JWT` means the login did not answer `200`: a `202` asks for the second factor
(`POST /api/v1/auth/login/2fa` with its `token` and a code, the JWT is in the
`Authorization` header of that answer), a `412` means the administrator never chose their own
password (sign in once in the screens first).

```bash
AUTH="Authorization: Bearer $JWT"
JSON='Content-Type: application/json'

# 1. Rename the administrator (account 1), then set its sheet password.
curl -sS -X PATCH "$CORE/api/v1/admin/users/1/" -H "$AUTH" -H "$JSON" -d '{"first_name":"Administrateur"}'
curl -sS -X PATCH "$CORE/api/v1/admin/users/1/password" -H "$AUTH" -H "$JSON" \
  -d "$(jq -n --arg p "$ADMIN_PW" '{new_password:$p}')"   # 204; sign in again for a new JWT

# Role ids of the instance.
curl -sS "$CORE/api/v1/admin/roles/" -H "$AUTH" | jq '.[] | {id, name}'

# 2 and 3. One account: create (temporary password), role, final password.
create_account() { # <email> <first name> <last name> <role id>
  local pw tmp id
  read -rs -p "Sheet password of $1: " pw; echo
  tmp="$(openssl rand -base64 24)"
  id=$(curl -sS -X POST "$CORE/api/v1/admin/users/" -H "$AUTH" -H "$JSON" \
    -d "$(jq -n --arg e "$1" --arg f "$2" --arg l "$3" --arg p "$tmp" '{email:$e,first_name:$f,last_name:$l,password:$p}')" | jq -r .id)
  curl -sS -X POST "$CORE/api/v1/admin/users/$id/roles/" -H "$AUTH" -H "$JSON" -d "{\"role_id\":$4}"
  curl -sS -o /dev/null -w '%{http_code}\n' -X PATCH "$CORE/api/v1/admin/users/$id/password" -H "$AUTH" -H "$JSON" \
    -d "$(jq -n --arg p "$pw" '{new_password:$p}')"
  echo "$1 -> account $id"
}
create_account employe@mairie360.fr Camille Durand <id of User>
create_account responsable@mairie360.fr Julien Moreau <id of Responsable>
create_account maire@mairie360.fr Isabelle 'Lefèvre' <id of Maire>
```

A `409` on the creation means the address is already taken (account kept from an earlier
run, or archived): see « Run it again » below. The password reset answers `204`; a `400`
names the rule the password breaks.

## Verification checklist

- [ ] The four accounts sign in on `https://login.<domain>/` with their sheet password, with
      no password change asked, and each shows its role (Administration → Users, or the
      profile).
- [ ] Signed in as the Employee, `https://elearning.<domain>/` lists « Prise en main de
      Mairie 360 » with its three modules; the course opens.
- [ ] As an administrator, the e-learning catalogue filter « Origine » → « Formations de
      l'outil » shows the course (origin `platform`).
- [ ] « Mot de passe oublié » on `https://login.<domain>/` for one of the accounts: the
      reset e-mail arrives in its `@mairie360.fr` mailbox (F5). Do not finish the reset, or
      the sheet password no longer works; if it was finished, set the sheet password again
      with an administrator reset.
- [ ] Do not start the course with a test account before the ATP: F53 to F55 play it from the
      start.

## Cleanup after the ATP

Only when the ATP team decides it; the data is not in the way of the instance otherwise.

1. **Archive the three accounts**: Administration → Users → each account → archive, or
   `curl -X DELETE "$CORE/api/v1/admin/users/<id>/" -H "$AUTH"`. The sessions end, the
   account keeps its history.
2. **Delete the course**: from its card in the e-learning catalogue, or
   `curl -X DELETE "$ELEARNING/api/v1/admin/formations/$COURSE/" -H "$AUTH"`.
3. **Give the administrator its first name back** if the team wants it (`Admin`, or a real
   name), and change its password away from the sheet's: the sheet is shared with the
   testers.

The data the ATP itself created (groups, projects, events, conversations, the tester's
Manager account) is removed by the ATP team in the same way if needed.

## Run it again

The steps are safe to replay: the enrolment is idempotent, a password reset can be repeated,
and an account or a course that already exists is kept (`409` on the account creation:
look the account up in Administration → Users and only redo its role and password). An
archived account still holds its address: to create it again, either restore it from the
database (`restore_user`) or erase it first (`POST /api/v1/admin/users/<id>/erase`, final)
and create it anew.
